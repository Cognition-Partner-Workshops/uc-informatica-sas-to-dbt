# Informatica → dbt → Snowflake walkthrough

This is a worksheet companion for the migration lead. It uses the standing Snowflake run, not a rebuild:

- Database: `DEVIN_MIGRATION_DEMO`
- Migrated schema: `DEVIN_MIGRATION_DEMO.DBT_INFORMATICA_RUN20260806`
- Baseline schema: `DEVIN_MIGRATION_DEMO.BASELINE_INFORMATICA_RUN20260806`
- Role / warehouse: `DEVIN_MIGRATION_DEMO` / `DEVIN_DEMO_WH`

The nine seeded source/state tables, 24 dbt views, seven migrated target tables, and seven baseline tables were present when these queries ran. No seed or dbt build was run for this walkthrough. Snowflake folds the unquoted model identifiers to uppercase; the fully-qualified identifiers below are therefore ready to paste into a worksheet.

For the recovered semantics and portability decisions, see [Informatica conventions](informatica_conventions.md). The expression-by-expression review is in the [transformation-expression inventory](informatica_expression_inventory.md).

### First differing column

This pattern reports the first differing column for a keyed target. Replace the key and column list for the target under investigation. The following is the actual `DEMO_TARGET6` query and returned `(0 rows)`.

```sql
WITH b AS (
    SELECT * FROM DEVIN_MIGRATION_DEMO.BASELINE_INFORMATICA_RUN20260806.DEMO_TARGET6
), m AS (
    SELECT * FROM DEVIN_MIGRATION_DEMO.DBT_INFORMATICA_RUN20260806.DEMO_TARGET6
)
SELECT COALESCE(TO_VARCHAR(b.ACCT_ID), TO_VARCHAR(m.ACCT_ID)) AS KEY,
       CASE
         WHEN b.ACCT_TYP IS DISTINCT FROM m.ACCT_TYP THEN 'ACCT_TYP'
         WHEN b.ACCT_DESC IS DISTINCT FROM m.ACCT_DESC THEN 'ACCT_DESC'
         WHEN b.CR8_DT IS DISTINCT FROM m.CR8_DT THEN 'CR8_DT'
         WHEN b.CRDT_LN IS DISTINCT FROM m.CRDT_LN THEN 'CRDT_LN'
         WHEN b.CLSR_DT IS DISTINCT FROM m.CLSR_DT THEN 'CLSR_DT'
         WHEN b.ACCT_STAT_CD IS DISTINCT FROM m.ACCT_STAT_CD THEN 'ACCT_STAT_CD'
         WHEN b.TX_ID IS DISTINCT FROM m.TX_ID THEN 'TX_ID'
         WHEN b.ACCT_KEY IS DISTINCT FROM m.ACCT_KEY THEN 'ACCT_KEY'
         WHEN b.TX_DTTM IS DISTINCT FROM m.TX_DTTM THEN 'TX_DTTM'
         WHEN b.TX_AMT IS DISTINCT FROM m.TX_AMT THEN 'TX_AMT'
         WHEN b.TX_TYPE_CD IS DISTINCT FROM m.TX_TYPE_CD THEN 'TX_TYPE_CD'
       END AS FIRST_DIFFERING_COLUMN
FROM b FULL OUTER JOIN m USING (ACCT_ID)
WHERE b.ACCT_ID IS NULL OR m.ACCT_ID IS NULL
   OR b.ACCT_TYP IS DISTINCT FROM m.ACCT_TYP
   OR b.ACCT_DESC IS DISTINCT FROM m.ACCT_DESC
   OR b.CR8_DT IS DISTINCT FROM m.CR8_DT
   OR b.CRDT_LN IS DISTINCT FROM m.CRDT_LN
   OR b.CLSR_DT IS DISTINCT FROM m.CLSR_DT
   OR b.ACCT_STAT_CD IS DISTINCT FROM m.ACCT_STAT_CD
   OR b.TX_ID IS DISTINCT FROM m.TX_ID
   OR b.ACCT_KEY IS DISTINCT FROM m.ACCT_KEY
   OR b.TX_DTTM IS DISTINCT FROM m.TX_DTTM
   OR b.TX_AMT IS DISTINCT FROM m.TX_AMT
   OR b.TX_TYPE_CD IS DISTINCT FROM m.TX_TYPE_CD
ORDER BY KEY
LIMIT 1;
```

### Query history

This proves the worksheet account executed the checks. It uses session-local `INFORMATION_SCHEMA.QUERY_HISTORY`, as does the verification script.

SELECT START_TIME, QUERY_ID, USER_NAME, ROLE_NAME, WAREHOUSE_NAME,
       EXECUTION_STATUS, QUERY_TEXT

## 5. Re-running against another schema

The standing objects are intentionally not rebuilt by this document. To run the workflow into a separate schema, provide the private-key path and an isolated schema:

```bash
export SNOWFLAKE_PRIVATE_KEY_PATH=/home/ubuntu/sf_key.pem
export SNOWFLAKE_SCHEMA=DBT_INFORMATICA_MY_RUN
source /home/ubuntu/venv-dbt/bin/activate
cd dbt/informatica
./run_workflow.sh --target snowflake
```

The workflow seeds first and then runs the three sessions in XML order. For warehouse-side checks:

```bash
python3 scripts/load_baseline_snowflake.py \
  --migrated-schema "$SNOWFLAKE_SCHEMA" \
  --baseline-schema BASELINE_INFORMATICA_MY_RUN
python3 scripts/verify_snowflake.py \
  --migrated-schema "$SNOWFLAKE_SCHEMA" \
  --baseline-schema BASELINE_INFORMATICA_MY_RUN
python3 scripts/parity_snowflake.py \
  --migrated-schema "$SNOWFLAKE_SCHEMA"
```

Use a separately loaded baseline schema for a new run. Do not point these commands at the protected `DBT_INFORMATICA` or `BASELINE_INFORMATICA` schemas. The Snowflake parity export uses the unmodified `tools/parity_diff.py`; the local DuckDB comparator environment remains `/home/ubuntu/venv-p2/bin/python` because it pins `pandas<3`.
