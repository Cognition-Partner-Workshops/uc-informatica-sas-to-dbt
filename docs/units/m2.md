## 1. Unit overview

`m_demo_mapping2` is an SCD-style insert/update detection mapping. It reads a flat-file
feed of general-ledger reference records, looks each record up against the existing
target table pre-image, and routes rows to an Insert instance or an Update instance of
the same physical target table.

- **Source**: `demo_source1` (Flat File) — columns `LEAD_CO_MNE`, `BRANCH_CO_MNE`,
  `MIS_DATE`, `ID`, `DESCRIPTION`, `SHORT_NAME`. Seed: `legacy/informatica/data/demo_source1.csv`
  (120 rows: 40 IDs that exist in the pre-image, 80 new IDs).
- **Lookup table**: `demo_target1` pre-image (Oracle target used as an unconnected-style
  lookup source). Seed: `legacy/informatica/data/demo_target1.csv` (57 rows, `Key` 1..57).
- **Targets** (both are instances of table `demo_target1`):
  - `demo_target1_INS` — new records (Insert router group), surrogate `Key` from sequence `SEQTRANS`.
  - `demo_target1_UPD` — changed existing records (Update router group) via Update Strategy `DD_UPDATE`.

Flow (from the XML): `demo_source1` → `SQ_demo_source1` (Source Qualifier) → `EXPTRANS`
(expression; embeds lookup `LKPTRANS` on `demo_target1` with condition `ID = ID1`, policy
"Use Any Value"; derives `New_Flag`, `MD5_src`, `MD5_tgt`, `Changed_Flag`, audit columns) →
`RTRTRANS` (router: `Insert` group `New_Flag='Insert'`, `Update` group `Changed_Flag='Update'`,
unconnected `DEFAULT1`) → Insert branch straight to `demo_target1_INS` with `Key` from
`SEQTRANS.NEXTVAL` (start 0, increment 1, current value 57, no cycle); Update branch through
`UPDTRANS` (Update Strategy `DD_UPDATE`, forward rejected rows) to `demo_target1_UPD`.

Key expressions in `EXPTRANS` (verbatim from the XML):

- `New_Flag = IIF(ISNULL(Key),'Insert')`
- `MD5_src = AES_DECRYPT(LEAD_CO_MNE1, SUBSTR(SHORT_NAME,1,3), 256)`
- `MD5_tgt = MD5(LEAD_CO_MNE || BRANCH_CO_MNE || MIS_DATE || DESCRIPTION || SHORT_NAME)`
- `Changed_Flag = IIF(NOT ISNULL(Key) AND (MD5_tgt != MD5_src),'Update')`
- `o_CREATED_BY = 'IDWUSER'`, `o_CREATED_TIME = SYSDATE`, `o_UPDATED_BY = 'IDWUSER'`, `o_UPDATED_TIME = SYSDATE`

## 4. Snowflake notes

Things in this unit's SQL a Snowflake deployment should review:

- **`MD5(...)` string concatenation with `||`**: Snowflake `MD5()` and `||` behave the
  same as DuckDB for non-NULL inputs, but `||` with any NULL operand yields NULL (same
  in both engines). None of the concatenated seed columns are NULL today; if real feeds
  can carry NULLs, wrap operands in `COALESCE` or use `CONCAT_WS` so the hash input is
  deterministic.
- **`AES_DECRYPT` has no Snowflake equivalent**: Snowflake has no built-in
  `AES_DECRYPT`; the closest are `DECRYPT`/`DECRYPT_RAW` (binary, different key
  semantics — passphrase-based `DECRYPT` raises an error on bad input rather than
  returning NULL). Since the legacy port is a dead expression (§5), the migration
  hard-codes its NULL result instead of porting the function — nothing to translate,
  but any Snowflake re-implementation must NOT attempt a literal port.
- **Sequence semantics**: the surrogate `Key` (`SEQTRANS`, current value 57) is
  implemented as `56 + ROW_NUMBER() OVER (ORDER BY id)`. In Snowflake, a native
  `SEQUENCE` object does not guarantee gap-free ordered assignment; keep the
  `ROW_NUMBER` formulation for deterministic parity.
- **`SYSDATE` pinning**: audit timestamps (`CREATED_TIME`/`UPDATED_TIME`) are pinned to
  `2024-01-31 00:00:00` via the dbt var `business_date`. In Snowflake, `SYSDATE()`
  returns UTC while `CURRENT_TIMESTAMP()` is session-timezone-local — keep the pinned
  var rather than either function.
- **Quoted mixed-case identifiers**: the target columns include mixed-case `"Key"`.
  Snowflake folds unquoted identifiers to UPPERCASE; the models correctly quote all
  target columns, and any downstream consumers must also quote `"Key"`.
- **`DD_UPDATE` (update strategy)**: the legacy Update branch corresponds to an
  `UPDATE`-flagged load. In Snowflake/dbt this would be an incremental model or
  `MERGE`; here it is materialized as a plain table of update-branch rows (currently
  always empty — §5), which is the faithful representation of the mapping's output.

## 5. Legacy dead path found by reverse engineering (formerly "known gap")

**Finding**: `demo_target1_UPD` receives **0 rows**, and no seed-data change can ever
exercise the Update branch, because the branch is structurally dead in the legacy
mapping itself:

- `EXPTRANS.MD5_src = AES_DECRYPT(LEAD_CO_MNE1, SUBSTR(SHORT_NAME,1,3), 256)` attempts
  to AES-decrypt `LEAD_CO_MNE1` — the *plaintext* lookup value from the pre-image, which
  was never AES-encrypted — using a 3-character passphrase. The decryption always fails,
  so `MD5_src` is **always NULL**.
- Therefore `MD5_tgt != MD5_src` evaluates to NULL (not TRUE), and
  `Changed_Flag = IIF(NOT ISNULL(Key) AND (MD5_tgt != MD5_src),'Update')` is **never**
  `'Update'`.
- Matched rows with changed attributes (the seed data deliberately contains 20 such
  rows: existing IDs whose `DESCRIPTION` ends in ` REVISED`) fall through to the
  unconnected `DEFAULT1` router group and are silently dropped.

The migration reproduces this behavior **exactly**: both the baseline runner
(`tools/informatica_baseline.py`) and the dbt model
(`dbt/informatica/models/intermediate/int_m2_change_detect.sql`) hard-code the NULL
`MD5_src`/`Changed_Flag` with comments citing this anomaly, so `demo_target1_UPD` is
0 rows on **both** sides and parity is VERIFIED (§3.4). This is intentional: the goal
of the migration is functional parity with the legacy system as it actually behaves,
not as it was presumably intended to behave.

**Recommendation for the business**: if the SCD update path is actually desired, the
fix belongs in a deliberate change request (compare `MD5_tgt` against an MD5 of the
pre-image row, e.g. `MD5(LEAD_CO_MNE1 || BRANCH_CO_MNE1 || MIS_DATE1 || DESCRIPTION1 || SHORT_NAME1)`),
applied to both the baseline and the dbt model in lockstep — not as a silent "fix"
during migration, which would break parity with the legacy system of record.
